# ADR029: Bounded RECURRENCE-ID instance timing edits

- Status: Accepted
- Date: 2026-10-03

## Context

ADR023 defines occurrence projection and preserves the original typed
RECURRENCE-ID when a detached event has moved. It currently sends occurrence
edits to the series editor because the gateway has no bounded instance-write
operation. A timing change for one occurrence must update the canonical
CalDAV resource without changing the master, losing unknown properties, or
mistaking a moved override's display time for its original recurrence
identity.

The current recurrence projector supports a bounded RRULE/RDATE subset and
preserves opaque recurrence data. The resource write uses one conditional
CalDAV update, so an instance override can be changed within the existing
single-resource ETag boundary. `RANGE=THISANDFUTURE` and unsupported recurrence
or timezone data remain opaque.

## Decision

1. The initial instance-edit phase supports timing changes for exactly one
   selected occurrence. Its write identifies the occurrence by the original,
   typed RECURRENCE-ID. The identity must be a member of the supported set
   generated by the master DTSTART, RRULE, or RDATE; detached overrides alone
   do not establish membership. An existing moved override is matched by its
   original RECURRENCE-ID, never by its current DTSTART. The public PATCH
   operation is `recurrence.occurrence` with the shape
   `{ action: 'set-timing', recurrenceId, timing, viewerTimezone }`. The
   `viewerTimezone` is required, must be in the bundled IANA set, and is
   projection context used for validation only; it does not change the stored
   recurrence identity or value kinds.
2. Creating an instance override clones the master VEVENT, preserving its
   UID, unknown properties, parameters, and supported same-event metadata. The
   clone removes the master's RRULE, RDATE, and EXDATE values and receives one
   RECURRENCE-ID and the selected timing. Updating an existing override changes
   only DTSTART and either DTEND or DURATION. It preserves the exact existing
   RECURRENCE-ID property and its parameters, the UID, and all other target
   properties. Unknown and safely distinguishable non-target siblings remain
   untouched in the resource.
3. Before producing a component, the codec requires one unambiguous master,
   one unambiguous target identity, supported recurrence and timezone data,
   an actual non-excluded recurrence candidate, and a single well-formed
   RECURRENCE-ID on every same-UID detached VEVENT. Duplicate or malformed
   identities, any RANGE parameter, a cancelled target, malformed target
   timing, and recurrence inputs whose candidate set cannot be established
   fail closed. The helper clones the target or master and does not mutate the
   parsed resource while preflighting.
   Timing validation keeps DATE endpoints as DATE and interprets floating
   DATE-TIME endpoints in the supplied viewer timezone; explicitly zoned
   endpoints use their own supported timezone. The codec validates the
   resulting half-open interval (`end` after `start`) with bundled zone rules
   and rejects local endpoints that cannot round-trip to the submitted wall
   time.
4. The first phase is timing-only. It does not add, copy, remove, inherit, or
   re-key VALARM data. If any same-UID VEVENT in the resource contains a
   VALARM, an instance timing write is rejected with an explicit explanation
   and every alarm remains unchanged. No alarm identity or Matrix reminder
   sidecar behavior is inferred for a detached override.
5. An effective edit to an existing detached component follows ADR025: use
   one injected clock snapshot, advance a valid SEQUENCE once, refresh valid
   DTSTAMP and LAST-MODIFIED, and never change CREATED. A newly-created
   detached component is the same event as its master, so it retains the
   master's CREATED value, refreshes valid DTSTAMP and LAST-MODIFIED, and uses
   the next valid master SEQUENCE (a missing value follows ADR025's zero
   default). Malformed, duplicate, unrepresentable, or exhausted revision
   metadata remains opaque and is preserved from the original content lines.
   The master revision is never changed by an instance timing edit.
6. Cancelling and restoring an occurrence continues to use the existing
   single-EXDATE operation. Ordinary series edits continue to edit the master.
   An edit launched from an occurrence must ask the user to choose that
   occurrence or the entire series before saving. The series option retains
   current whole-series behavior; the instance option is available only for
   the supported timing-only operation above and displays its failure reason
   when a preflight rejects it.
7. This decision does not define “this and following” semantics. That work
   remains an open design question: evaluate a bounded, single-resource
   `RANGE=THISANDFUTURE` update against supported RFC behavior and evaluate
   finite-series materialization into detached overrides against the existing
   one-resource conditional-write boundary. Do not implement a generic RRULE
   split or claim following-scope completion from this decision.

## Consequences

Supported instance timing edits remain within one canonical CalDAV resource
and use one ETag-protected update. Unsupported or ambiguous cases retain their
source components and return a fail-closed result. The user can distinguish
one-occurrence timing changes from existing whole-series edits, while alarm
behavior stays explicitly unsupported for this phase. “This and following”
still needs its own evidence-backed semantics decision.

## Validation

Codec tests cover generated-candidate membership rather than arbitrary
same-kind dates, original identity for moved overrides, exact parameter
preservation, unknown sibling preservation, EXDATE rejection, alarm rejection,
resource immutability during preflight, and revision metadata behavior for
both created and updated detached components. UI scope-prompt and explanation
tests belong with the editor integration. Cross-client recurrence
interoperability remains a separate release validation gate.
