# ADR012: Write one recurring event instance within its CalDAV resource

- Status: Accepted
- Date: 2026-09-26

## Context

The widget presents a recurring event as separate visible occurrences, while
CalDAV stores the master and detached exceptions together in one `.ics`
resource. A resource-wide edit or delete can change every occurrence or remove
the full series. A moved instance also keeps its original `RECURRENCE-ID`, so
its current `DTSTART` cannot be used as the edit identity.

## Decision

- Add explicit single-instance update and cancellation operations. Each request
  carries the calendar ID, backing resource URL, and original typed
  `RECURRENCE-ID`. The gateway whitelists editable occurrence fields and
  authorizes the operation as `update-event` before reading from CalDAV.
- Update exactly one detached `VEVENT` matching the master UID and typed
  original `RECURRENCE-ID`. If the occurrence is generated by the master
  `RRULE` or an `RDATE`, create a detached `VEVENT` in that same resource.
  Preserve DATE versus DATE-TIME and UTC, floating, or TZID identity.
- Preserve the fetched VCALENDAR when writing, including the master, sibling
  overrides, VTIMEZONE, and properties the domain model does not understand.
  A moved instance retains its original `RECURRENCE-ID` even when its
  `DTSTART` changes.
- Cancel one instance by adding or updating a same-resource detached `VEVENT`
  with `STATUS:CANCELLED`. Do not delete the resource or add an `EXDATE` to the
  master.
- Require the resource ETag and write with `If-Match`. A conflict returns an
  error; clients do not automatically retry. Users reload the occurrence before
  trying again.
- Keep “this and following” and whole-series edit scopes separate. This API
  only edits or cancels one instance.

## Consequences

Single-instance changes remain interoperable with CalDAV clients that read
standard detached VEVENT overrides. The CalDAV resource remains the canonical
record, and its conditional write protects unrelated master and sibling data
from stale replacement. Following-instance and series-wide edit semantics need
their own explicit operations and acceptance criteria.
