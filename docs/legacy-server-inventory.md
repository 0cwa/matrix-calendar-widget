### SDK listeners outside Nest dispatch and unmatched subscriptions

`MatrixClient` has direct listeners in addition to the `MatrixServer` adapter. `app.module.ts:227-234` always installs `AutojoinUpgradedRoomsMixin` for `room.archived`; when `enable_welcome_workflow` is false it also installs `AutojoinRoomsMixin` for `room.invite`, which joins the invited room. When welcome is enabled, that autojoin listener is omitted and `WelcomeWorkflowController` handles the invite instead. `MatrixServer.onModuleInit` starts the optional room migration directly before Nest handlers are attached when `enable_control_room_migration` is true (`MatrixServer.ts:187-198`). These direct listeners and startup effects are not `@EventPattern` handlers.

All four `BotEventType` listeners are attached by `MatrixServer.listen`, but not every delivered event has a Nest handler:

- `room.leave` has no registered `@EventPattern`; `processEvent` only clears the cached bot-membership timestamp for that room before handler lookup (`MatrixServer.ts:293-295`).
- `room.event` + `m.room.encrypted` is included in the default sync filter, but no controller registers that pair.
- `room.event` + `m.room.message` has no registered pair; the command handler uses the separate `room.message` SDK trigger.
- If `MATRIX_FILTER_APPLY=false`, `MatrixServer` starts without the source filter, so other event types may be delivered and logged as having no matching handler. The complete runtime set then depends on SDK and server delivery.
- `room.invite` has one mapped pair (`m.room.member`); `room.message` has one mapped pair (`m.room.message`). Other combinations have no handler.

### Dispatch checks

The default filter requests `m.room.member`, `m.room.power_levels`, `m.room.encrypted`, `m.room.message`, and the eight listed `net.nordeck.meetings.*` timeline types; `MATRIX_FILTER_APPLY` defaults true and the timeline limit defaults to 50 (`MatrixServer.ts:136-178`; `configuration.ts:220-224`). This is a sync subscription filter, not a per-handler enable switch. `MatrixServer.processEvent` first rejects absent/incomplete event objects, updates invite/leave timestamp state, and drops events older than `MATRIX_SERVER_EVENT_MAX_AGE_MINUTES` (default five). For known non-state `net.nordeck.meetings` room events, it also requires the event timestamp to be at or after the bot's membership timestamp; failure to obtain that timestamp drops the event (`MatrixServer.ts:273-359,395-407`). It then normalizes the exact trigger/type pair and looks up a Nest handler (`:361-382`).

The meeting controller's HTTP routes are denied with 404 and its Matrix RPC routes are denied by `LegacyMeetingDisabledGuard` before service invocation. Welcome methods and guest-power methods retain their separate configuration checks. `CommandService` checks `enable_welcome_workflow` for legacy commands, while `!calendar` is handled before that branch. The exception filter's private-room error send has its own `enable_private_room_error_sending` setting. Source defaults for welcome, migration, guest-power changes, and private-room error sending are false (`configuration.ts:193-203,226-235`); **the target values for all these settings, `MATRIX_FILTER_APPLY`, event-age limit, and timeline limit are unknown**. Default-off source values do not establish that a target operator left a setting disabled.

For registered legacy NIC room events, `eventIsRegisteredByBot` applies the post-join timestamp filter and `MatrixServer` attempts the success reaction only after handler processing returns (`MatrixServer.ts:395-407,383-390`). The guard still denies the meeting controller route; the subscription and attempted dispatch remain in source. ADR042 explicitly preserves ordinary autojoin while welcome behavior is disabled and preserves compatibility opt-ins for welcome/private-error-room behavior (`docs/adrs/adr042-calendar-only-legacy-meeting-apis-disabled.md:32-39,63-86,98`). Thus “disabled by default” is not “unreachable in every supported deployment.”
