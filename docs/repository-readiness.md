## Current code boundaries

- Room reads, event writes, reminder configuration, reminder delivery, and action notices have independent default-off gates. A configured database enables persistence only; it does not by itself start delivery.
- The Matrix event sender is actor context and attribution only; the CalDAV identity for room operations is the configured application-service principal.
- The M7 bot remains a bounded fallback. The primary widget uses the authorized room context and bound calendar; actual Element-client acceptance remains untested.
- Whole-room reminder notifications in unencrypted rooms are the only accepted initial delivery target. Encrypted scheduled reminders, email, consent flows, individual recipients, and per-user bot proof are deferred.
- CalDAV alarm editing is metadata authoring. Scheduled Matrix delivery is a separate opt-in capability.
- Room-target widget create/update/delete notices use the SDK crypto-aware send path when needed; scheduled reminders use the native appservice transport and refuse encrypted rooms. Neither path's tests establish general encrypted-room client support.
- The Matrix bot SDK calls used for action notices have a 60-second default request timeout and no abort adapter. Scheduled reminder delivery uses a separate native transport with a two-second request timeout. A room-target CalDAV mutation succeeds independently of its best-effort notice.

## Source-document caveat

The README and threat model have been aligned to this source snapshot. They record repository behavior and remaining acceptance gates; neither is evidence of an actual Element client, etke-managed host, or production deployment. The deployment and upgrade documents distinguish the project-owned Compose volumes from an etke-managed Radicale `/data` store, but their procedures have not been executed on a production host.
